Azure Networking

Virtual Networks, NSG, ASG, Peering, Load Balancing, VPN Gateway, Firewall

Virtual Networks (VNet)
Definition: An Azure Virtual Network (VNet) is a logically isolated, private IP network hosted in Azure. It enables Azure resources (VMs, containers, databases) to securely communicate with each other, the internet, and on-premises infrastructure — without traffic ever traversing the public internet unless explicitly configured to do so.

Core Components

01
Address Space
CIDR range assigned to the VNet (e.g., 10.0.0.0/16). All private IPs for resources inside the VNet are drawn from this pool. A /16 gives 65,536 addresses.
02
Subnets
Sub-divisions of the address space (e.g., 10.0.1.0/24). Each subnet isolates a tier of the architecture. Azure reserves 5 IPs per subnet — the remaining 251 are usable on a /24.
03
Network Security Groups (NSG)
Stateful Layer 3/4 firewall attached to a subnet or NIC. Enforces allow/deny rules on inbound and outbound traffic based on 5-tuple: protocol, port, source, destination, action.
04
DNS Settings
Either Azure-provided (168.63.129.16) or custom DNS servers. Controls name resolution for all VMs inside the VNet — critical for domain-joined VMs and on-premises resolution.
05
Route Tables
Custom User-Defined Routes (UDRs) override Azure's default system routes. Used to force traffic through a firewall NVA or control inter-subnet routing paths.
06
VNet Peering / Gateway
Connect VNets to each other (peering) or to on-premises (VPN/ExpressRoute gateway). Peered traffic stays on Azure backbone — not the public internet.

Subnets & 3-Tier Architecture
What is a Subnet?

A subnet is a range of IP addresses carved from the VNet's address space. Each subnet can be independently secured with an NSG, given its own route table, and assigned to a specific service endpoint. Azure reserves 5 IP addresses per subnet (.0 network, .1 default gateway, .2–.3 DNS, .255 broadcast) — so a /24 yields 251 usable IPs.

Tier-by-Tier Role Analysis

WebTier-Subnet — Presentation Layer
  • Hosts: IIS, Apache, Nginx web servers (WebServer-VM01, VM02, VM03)
  • Accepts: HTTP (80) and HTTPS (443) from the internet
  • Accepts: RDP (3389) only from Management-Subnet (10.0.10.0/24)
  • Cannot: directly connect to DataTier — all requests must pass through AppTier
  • Has a public IP or sits behind a Public Load Balancer
  • Security posture: least restricted tier for internet traffic, but RDP locked down
AppTier-Subnet — Business Logic Layer
  • Hosts: Application servers running APIs or business logic (AppServer-VM01)
  • Accepts traffic: only from WebTier-Subnet on port 8080 (TCP)
  • Cannot be accessed from the internet directly — no public IP assigned
  • Communicates to: DataTier on SQL port 1433
  • Protected by: AppTier-NSG which denies all except WebTier source
  • Uses: Internal Load Balancer (AppTier-ILB) at private IP 10.0.2.100
DataTier-Subnet — Data Persistence Layer
  • Hosts: DBServer-VM01 (SQL Server / MySQL)
  • Accepts: only port 1433 (SQL) from AppTier-Subnet
  • Most restricted tier — no internet exposure whatsoever
  • No public IP. Private IP only: 10.0.3.x
  • Direct access from WebTier or internet: blocked by NSG (Deny rule)
  • Data here is the crown jewel — all other layers serve to protect it
Management-Subnet — Jump Box / Admin Plane
  • Hosts: JumpBox-VM01 — the single authorised entry point for admins
  • Admins RDP into JumpBox first (from allowed IPs only), then RDP from JumpBox to any VM
  • Prevents: direct internet RDP to production VMs (common attack vector)
  • Acts as: an audit chokepoint for all administrative activity
  • CIDR: 10.0.10.0/24 — deliberately non-sequential to avoid accidental routing overlap

Your own DNS servers (AD DNS controllers). VMs restart NIC after changing — always reboot after update.

When to Use Custom DNS

1
Active Directory Integration
Domain-joined VMs must resolve DC hostnames. Azure DNS can't do this — you must point to your own Domain Controllers as DNS servers.
2
Hybrid Connectivity (VPN/ExpressRoute)
On-premises server names (e.g., fileserver.corp.local) need to resolve inside Azure. Custom DNS server forwards requests to on-premises DNS.
3
Conditional Forwarding
Route *.internal.corp queries to corporate DNS, everything else to internet. Requires custom DNS server with forwarding rules.
4
Security / DNS Filtering
DNS appliances like Cisco Umbrella block malicious domains at the DNS level. Must configure VMs to use the security DNS server as their resolver.
5
Cross-VNet / Multi-Cloud Resolution
Complex environments where names span multiple VNets or cloud providers require a custom DNS hub that knows all name spaces.
Network Security Groups (NSG)
Definition: An NSG is a stateful Layer 3/4 packet filter containing a list of security rules. It can be associated with a subnet (protects all VMs in that subnet) or a NIC (protects a single VM). Azure evaluates rules by priority — lowest number wins. If no rule matches, the default deny-all applies.

The 7 Fields of an Inbound Security Rule

FieldValuesPurpose
Priority100 – 4096Order of evaluation. Lower = higher priority. First matching rule wins.
NameString (unique)Human-readable identifier (e.g., Allow-HTTP, Deny-All-Inbound)
Port80, 443, 3389, *, rangesDestination port the rule targets. * = all ports.
ProtocolTCP, UDP, ICMP, *Network protocol. * matches all.
SourceIP, CIDR, Service Tag, ASGWhere traffic originates. e.g., Internet, 10.0.10.0/24, ASG-WebServers
DestinationIP, CIDR, Service Tag, ASGWhere traffic is going. Usually VirtualNetwork for inbound.
ActionAllow / DenyWhat to do when the rule matches the packet.

AppTier-NSG Rules (Inbound)

Port 8080 · TCP · Source: 10.0.1.0/24 (or ASG-WebServers) → AppTier. Only web servers talk to app servers.
110
Allow-RDP-From-Mgmt ALLOW
Port 3389 · TCP · Source: Management-Subnet. Admin access via JumpBox only.
4096
Deny-All-Inbound DENY
Port * · * · * → *. No internet traffic reaches AppTier.

The Deny-All-Inbound at Priority 4096 — Why It Matters

Purpose: Zero-trust default enforcement.
  • Last resort catch-all: 4096 is the highest allowed custom priority (lowest precedence). Every packet that doesn't match any Allow rule reaches this and gets dropped — unconditionally.
  • Defence in depth: Explicit deny surfaces intent in the security rule set. Without it, Azure default rules might still pass VNet-originated traffic you didn't account for.
  • Compliance posture: ISO 27001, SOC 2, and PCI-DSS require a default-deny stance. This rule documents it in audit trails.
  • Mistakes protection: A misconfigured Allow rule at priority 200 for the wrong port is bad — but at least this catches anything that slips through all your other rules. It's the safety net below all your allows.

NSG Association Rules

iNSGs can be attached to subnets (applies to all VMs in the subnet) and/or NICs (applies to one specific VM). When both subnet-level and NIC-level NSGs exist, both are evaluated — subnet NSG first for inbound, NIC NSG first for outbound.
Application Security Groups (ASG)
What is an ASG?

An ASG is a logical grouping of VMs based on their application role — not their IP address. Instead of writing NSG rules like "allow traffic from 10.0.1.4 and 10.0.1.5 and 10.0.1.12...", you write "allow traffic from ASG-WebServers". When a new web server VM is added and assigned to ASG-WebServers, it automatically inherits all the rules — no IP address updates needed.

ASGs in the Lab

ASG-WebServers

Contains: WebServer-VM01, VM02, VM03. Used as source in AppTier-NSG rules. Any new web VM added here auto-gets AppTier access.

ASG-AppServers

Contains: AppServer-VM01. Used as destination in AppTier-NSG. Destination changes to ASG-AppServers instead of an IP range.

Benefits of ASGs Over IP-Based Rules

IP-Based Rules (Old Way)
  • Must specify exact IPs or CIDR ranges
  • Adding a new VM = update every NSG rule
  • IPs change if VM is deallocated/reallocated
  • Rules become unmaintainable at scale
  • No semantic meaning — rule says "10.0.1.4" not "web server"
ASG-Based Rules (Better)
  • Group by role: ASG-WebServers, ASG-AppServers
  • Adding VM = assign to ASG. Rules auto-apply.
  • IP-independent — membership is by assignment, not address
  • Scales cleanly — rule count stays constant
  • Self-documenting — rules read like intent

NSG Rule Using ASGs (Modified Allow-From-WebTier)

100
Allow-From-WebTier (ASG version)
Source: ASG-WebServers · Destination: ASG-AppServers · Port: 8080 · TCP · Allow. Semantically: "Any server in WebServers group can reach any server in AppServers group on 8080." Adding VM03 to ASG-WebServers = instant access. No rule edit needed.
VNet Peering
What is VNet Peering?

VNet Peering connects two Azure VNets so resources in each can communicate as if they're on the same network, using Azure's backbone — never the public internet. Traffic is private, low-latency (<1ms within same region), and high-bandwidth. Peering is non-transitive: A↔B and B↔C does NOT give A↔C connectivity.

Peering Settings Explained

S1
Allow Virtual Network Access
YES — Allows resources in the remote VNet to communicate with resources in this VNet. If set to No, peering exists but traffic is blocked.
S2
Allow Forwarded Traffic
YES — Allows traffic that originated outside the remote VNet (e.g., from a third VNet via NVA) to be forwarded through the peering. Required for hub-spoke topologies.
S3
Allow Gateway Transit
NO (in this lab) — If YES, the remote VNet can use this VNet's VPN Gateway. Used when a hub VNet has a gateway and spokes need on-premises access via it.
S4
Use Remote Gateways
NO — The spoke VNet uses the hub's gateway. Only one side can have this ON. Requires gateway transit on hub side.

Exam-Critical Facts on VNet Peering

  • Latency: Extremely low (<1ms same region). The lab test showed RTT = 0ms.
  • Cross-region: Yes — Global VNet Peering supported. Slightly higher latency than same-region.
  • Non-transitive: DevTest-VM01 can ping WebServer-VM01 (peered), but cannot reach DBServer-VM01 without explicit NSG rules allowing it.
  • No gateway needed: Peering works without a VPN gateway — it uses Azure's internal backbone.
  • Cost: Peering is charged per GB of data transferred (inbound and outbound). Same-region is cheaper than cross-region.
  • No overlapping CIDRs: VNets with overlapping address spaces cannot be peered.
Load Balancing (Full)
Azure Load Balancer — Overview

Azure Load Balancer is a Layer 4 (TCP/UDP) load balancer that distributes incoming traffic across healthy backend instances. It uses a 5-tuple hash (source IP, source port, dest IP, dest port, protocol) by default. It does not inspect Layer 7 (HTTP headers, URLs) — that requires Azure Application Gateway. Two types exist: Public (internet-facing) and Internal (private).

Load Balancer Components — Deep Dive

C1
Frontend IP Configuration
The public (or private) IP address that clients connect to. Traffic arriving here is redirected to the backend pool. Always use Static IP for LBs — dynamic IPs change on restart.
C2
Backend Pool
The group of VMs (or NICs) that serve traffic. The LB distributes connections across healthy members. Requires VMs to be in the same VNet and region as the LB.
C3
Health Probe
Periodically pings backend VMs to check if they're alive. HTTP probe hits a URL every 5 seconds. After 2 consecutive failures, the VM is removed from rotation. Prevents traffic going to dead VMs.
C4
Load Balancing Rule
Maps frontend port to backend port with a specific protocol. Defines session persistence (None = distribute freely, Client IP = sticky sessions) and idle timeout.
C5
Inbound NAT Rule
Maps a specific frontend port to a specific backend VM. Example: LB port 50001 → WebServer-VM01 port 3389 (RDP). Allows direct admin access to individual VMs via the single LB public IP.

Health Probe Configuration

HTTP-HealthProbe
  • Protocol: HTTP — actively requests the path and expects HTTP 200
  • Port: 80 — standard web port
  • Path: / — root URL. Can be a custom health endpoint like /health
  • Interval: 5 seconds — LB checks each backend every 5s
  • Unhealthy Threshold: 2 consecutive failures → VM removed from pool
  • Recovery: When VM starts responding, it re-enters the pool automatically
iHTTP probes are smarter than TCP probes — they verify the web application is actually running, not just that the port is open. Always prefer HTTP probes for web workloads.

Internal Load Balancer — AppTier-ILB

Configuration
  • Name: AppTier-ILB · Type: Internal · SKU: Standard
  • VNet: VNet-Production · Subnet: AppTier-Subnet
  • Frontend Private IP: 10.0.2.100 (Static) — this is what WebServers call
  • Backend Pool: AppServer-VM01 (any additional app servers)
  • Health Probe: TCP probe on port 8080
  • LB Rule: Port 8080 → backend port 8080
Why ILB? The app tier must never be exposed to the internet. WebServer-VM01 calls 10.0.2.100:8080 — the ILB distributes this to whichever app server is healthy. If you scale out to 3 app servers, only the ILB private IP needs updating in WebTier config. VMs in peered VNets (DevTest-VM01) can also access the ILB via VNet peering since the ILB has a private IP.

Session Persistence Options

None (Default)

5-tuple hash. Best throughput and distribution. No stickiness — user may hit different backend on each request. Good for stateless apps.

Client IP (2-tuple)

Same source IP always hits same backend. Useful for apps storing session state locally (shopping carts, file uploads). Breaks if user changes IP.

Client IP + Protocol (3-tuple)

Source IP + protocol determines backend. Useful for mixed TCP/UDP apps or when protocol matters. More specific than 2-tuple.

VPN Gateway
What is a VPN Gateway?

A VPN Gateway is a specific type of Virtual Network Gateway that sends encrypted traffic between Azure VNets and on-premises locations over the public internet (IPsec/IKE tunnels). It can also connect VNets to each other. Each VNet can have only one VPN Gateway. Deployment takes 30–45 minutes as it provisions redundant VMs internally.

Prerequisites

P1
GatewaySubnet
Must be named exactly "GatewaySubnet" — Azure enforces this. CIDR: 10.0.255.0/27 (32 addresses). Should not host any other resources. The /27 ensures enough IPs for gateway redundancy.
P2
Public IP for Gateway
VPNGateway-PIP — the public IP address that on-premises devices connect to. Must be Static with Standard SKU for reliable VPN connectivity.

VPN Connectivity Options

Site-to-Site (S2S)

On-premises VPN device (Cisco, Fortinet, Palo Alto) connects to Azure VPN Gateway over IPsec/IKE. Persistent, always-on connection. Requires a public IP on-premises side and a Local Network Gateway in Azure representing the on-premises network.

Point-to-Site (P2S)

Individual client machine connects to Azure VNet via VPN client software. Address pool: 172.16.0.0/24. Tunnel types: OpenVPN (SSL) or IKEv2. Auth: Azure certificate, Azure AD, or RADIUS. Used for remote workers.

VNet-to-VNet

Two Azure VNets connected via their VPN Gateways. Alternative to VNet Peering — encrypted, traverses public internet, higher latency and cost. Useful for cross-subscription or cross-tenant connectivity where peering is not available.

ExpressRoute

Dedicated private circuit (not internet-based) between on-premises and Azure via a connectivity provider. Much higher bandwidth (up to 100 Gbps), lower latency, SLA-backed. Used for large enterprises with consistent high-throughput needs. Uses ExpressRoute Gateway, not VPN Gateway.
